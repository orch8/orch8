# Adapter selection implementation

## Outcome

Implemented in `/home/hermes/projects/orch8-adapter-selection`, branch `fix/v2-adapter-selection`, created from fetched `origin/v2` at `17e254e`. Changes remain uncommitted for independent review. No push, merge, main-branch modification, cancellation work, permission-policy change, or provider integration.

`resolveAdapter` now rejects every explicit unsupported name before invoking an adapter. Empty strings, whitespace, misspellings, prototype property names and extra registry properties do not select Claude or another adapter. Exact `claude_local` and `codex_local` names still resolve. Only null/undefined legacy values retain the Claude default. API schemas still reject explicit null and allow omission, preserving the distinction between API validation and legacy resolver compatibility.

## Call-site inspection

- Heartbeat resolves inside its existing execution try/catch before run-log setup, configuration preparation and `runAgent`. Unsupported persisted types now produce a failed run with the selection error through existing error handling.
- Chat resolves before inserting its assistant/run rows or invoking `runAgent`. Existing catch broadcasts the selection error, including a null message ID when no assistant row exists. This existing error path was left unchanged and tested.
- Adapter environment-test route already validates names against `ADAPTER_TYPES` and returns 400 before calling the resolver or environment probe. Compatibility tests cover both valid names and invalid names.
- Server creates exactly Claude and Codex adapters. Both heartbeat and chat legacy single-adapter injection paths remain unchanged. Their existing suites pass.
- Agent create/update schemas already constrain explicit types and permit omission. Database-backed omission tests exercise the persisted Claude default. Resolver tests cover null/undefined directly.
- Only heartbeat and chat call `runAgent` in production; no new provider dispatch path was added.
